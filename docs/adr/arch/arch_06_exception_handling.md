# Architecture Decision Record: Exception Handling Strategy

## Context & Problem

以前のコードベースでは、多くの場所（コアロジックやUseCase層など）で `catch (Exception ex)` を用いて予期せぬ例外を捕捉し、ログに出力するのみで処理を継続（またはnullを返却）するパターンが散見されていました。

このアプローチには以下の深刻な問題がありました。
1. **サイレントフェイラー（Silent Failure）**: 本当はアプリケーションの状態が壊れているにもかかわらず、エラーが隠蔽され、UIが中途半端な状態で止まったり、処理結果が空のまま正常終了扱いされたりする。
2. **デバッグの困難化**: `NullReferenceException` などの「あってはならないバグ」が呼び出し元に伝播せず、中央のクラッシュハンドラーにも到達しないため、クラッシュレポートとして収集・検知できない。
3. **ロジックの複雑化**: すべての層でエラーハンドリングとリトライ・フォールバックを意識する必要が生じ、見通しが悪化する。

## Decision

以下の例外ハンドリング戦略をシステム全体に適用します。

### 1. 予期しない例外はキャッチせずクラッシュさせる (Fail Fast)
- **`catch (Exception)` の使用を原則禁止**します。
- メモリアクセス違反やオブジェクト状態の不整合（`NullReferenceException`, `ArgumentException`, `InvalidOperationException` など）は、プログラムのバグを示しています。これらは局所的にキャッチして握りつぶさず、上位に伝播させます。
- 最終的に `App.xaml.cs` の `DispatcherUnhandledException` や `CurrentDomain.UnhandledException` に到達し、**中央のクラッシュレポートダイアログを表示してアプリケーションを安全に終了（クラッシュ）**させます。

### 2. 予測可能なエラーのみを個別キャッチする
- 外部リソース（ファイルIO、オーディオライブラリ、ネットワーク）へのアクセスなど、コントロール不可能な事象に起因する例外のみを、**具体的な例外型（例: `IOException`, `UnauthorizedAccessException`, `FormatException`）** を指定してキャッチします。
- `catch (Exception ex)` を使用せざるを得ない外部ライブラリ（NAudio等）のケースでは、C# 6 の例外フィルター（`when` 句）を使用して、想定される具体的な例外のみを捕捉するように制限します。

### 3. ドメインエラーは Result パターンを使用する
- バリデーションエラーや「設定ファイルが存在しない」といったビジネス上のエラー状態は、例外機構（`throw`）を使わず、`OptimizationUseCaseResult<T>.Failure("...")` のような戻り値の Result パターンで表現します。
- 例外は「異常事態」の表現にのみ特化させます。

## Consequence

- **利点**: バグがサイレントに無視されることがなくなり、開発時および運用時の不具合検知が劇的に早くなります（Fail Fastの原則）。
- **利点**: コアのパイプラインやUseCaseのコードから冗長な `try...catch` ブロックが消え去り、可読性が向上します。
- **欠点**: これまで「なんとなく動いていた」箇所が、明確なエラーとして表面化しやすくなります。しかし、これはシステムの健全性を保つために必要なトレードオフと判断します。
