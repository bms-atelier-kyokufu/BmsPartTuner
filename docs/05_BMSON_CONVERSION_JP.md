# Bmson から BMS へのダウンコンバート・システム

BMS Part Tuner は、BMS の最適化機能に加えて、**bmson 形式から BMS 形式への高パフォーマンスなダウンコンバート**機能を備えています。
本ドキュメントでは、数千個の音声スライス処理を伴う複雑なダウンコンバートを、限られたメモリと CPU リソースで高速かつ安全に処理するためのアーキテクチャと最適化手法について解説します。

## 1. 変換ワークフローの分離 (Pipeline Architecture)

bmson から BMS への変換は、単なる JSON のデシリアライズにとどまらず、メタデータ変換、音声特徴の抽出、音声波形の切り出し（スライス）、ファイル出力といった多数のステップを内包する巨大な処理です。
これをモノリシックな処理として実装すると、保守性とテスト容易性が著しく低下します。

本プロジェクトでは、この問題を解決するために **Context-based Pipeline Architecture** を採用しています。

- **`BmsonConversionContext`**: ワークフロー全体で共有すべき状態（入力データ、中間生成物、進捗状況など）を保持する専用のコンテキストクラス。
- **`BmsonConversionPipeline`**: 個別の処理ステップ（Step）を順次実行し、コンテキストを引き回すパイプライン。各 Step は `IConversionStep` などのインターフェースを実装し、単一責任の原則（SRP）に従って独立してテスト可能です。

これにより、複雑なダウンコンバート処理の内部状態がカプセル化され、並列処理時のスレッドセーフティも向上しています。

## 2. Flyweight Pattern によるメモリ最適化と OOM 回避

bmson 形式の最大の特徴は、「1つの長尺なベース WAV ファイルから、指定した開始位置（`offset`）と長さ（`duration`）で必要な部分だけをスライスして発音する」仕組みにあります。
1つの bmson ファイルには、数百から数千ものスライス定義が存在します。

ダウンコンバート時、これらすべてのスライス音声に対して個別に `float[]`（波形データ）をヒープメモリに割り当てると、同じベース波形を何度もメモリ上に複製することになり、容易に **OutOfMemoryException (OOM)** を引き起こします。

この課題に対し、本システムは **Flyweight パターン**に基づくアプローチ（`PointerSoundData`）を採用しています。

- **参照の共有**: スライスされた音声オブジェクトは、実際の波形配列を保持しません。代わりに、ベースとなる音声データへの参照と、自身の開始インデックス、長さを保持します。
- **`ReadOnlySpan<float>` の活用**: 波形データが必要になった際は、ベース波形配列から `.AsSpan(start, length)` として切り出して返却します。
  これにより、データコピー（アロケーション）をゼロに抑え、どれだけスライス数が増えてもベース波形1つ分のメモリしか消費しない極限の最適化を実現しています。

## 3. 音声スライス切り出しの 2-Level Cache 戦略

bmson のノート配列を処理して物理的なスライス WAV ファイルを出力するフェーズにおいて、別のパフォーマンスボトルネックが存在しました。
それは、同一パラメータ（`fileName`, `offsetSec`, `durationSec`）に対するスライス要求が何度も重複して発生することです。

従来は毎回無音トリミング走査を行っていましたが、数万回の要求が重なると全体で数百ミリ秒〜数秒の遅延（塵積もって山となる状態）が発生します。
これを回避するため、以下の **2段階キャッシュ (2-Level Cache)** 機構を実装しました。

1. **L1 Request Cache (O(1) ルックアップ)**
   要求されたパラメータ文字列（例: `fileName|startByte|lengthBytes`）をキーとして、過去に生成したファイル名を即座に返します。ヒットした場合、高負荷な波形へのアクセスや無音トリミング計算を**完全にスキップ**できます。

2. **L2 Slice Cache (物理ファイルの重複生成防止)**
   無音トリミング計算を通過し、実際に物理ファイルへ書き出す段階でのキャッシュです。並列処理によるファイル I/O の競合を防ぐため、`Lazy<string>` を用いてスレッドセーフかつ非同期にファイルを生成・キャッシュします。

LINQ による `GroupBy` 事前集計等も検討されましたが、中間コレクションのアロケーションによる GC ポーズを避けるため、現在の「リクエスト駆動＋L1キャッシュ」というアロケーションフリーなアプローチを採用しています。

## 4. 数理モデルに基づくスコア (TOTAL) 変換

bmson における `total` 値（ゲージの回復量）は、IIDX の「デフォルトゲージ回復量（100%）」に対するパーセンテージで指定されます。
一方、標準的な BMS 形式（`#TOTAL`）では、回復量を絶対値の「実数」で指定する必要があります。この変換を正しく行わなければ、プレイ感が大きく損なわれます。

本システムでは、有名な BMS 解析スクリプトで採用されている **「black train 近似式」** を数学的モデルとして導入し、ノーツ数からデフォルト回復量を逆算しています。

ノーツ数 $N$ におけるデフォルト TOTAL 値 $T_{default}$ は次のように計算されます：

$$
T_{default} = \max\left(260.0, \frac{7.605 \cdot N}{0.01 \cdot N + 6.5}\right)
$$

実際の BMS 出力値 $T_{actual}$ は、bmson の `total` 値（$T_{\%}$）を用いて以下のように求められます：

$$
T_{actual} = T_{default} \cdot \left( \frac{T_{\%}}{100.0} \right)
$$

この数理モデルにより、bmson 制作者の意図したゲージ回復量（パーセンテージ）を、BMS 上で数学的に極めて正確に再現しています。
