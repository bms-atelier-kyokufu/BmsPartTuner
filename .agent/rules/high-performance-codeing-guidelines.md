# BMS Part Tuner - C# 高パフォーマンス・コーディング規約

## 0. 基本方針と設計思想 (Philosophy)

BMS Part Tuner（WPFを用いたWAV類似度判定・統合・最適化エンジン）において、「滑らかなUIの維持」と「数万個の音声ファイルの超高速比較（8000x Speedupの達成）」を両立させるため、本規約は「二層構造アーキテクチャ」の設計思想を採用します。

1. **通常領域 (Cold/Warm Path):** UIの初期化、設定の読み込み、汎用的なビジネスロジックなどは、C# 14 / .NET 10 標準の規約に準拠し、可読性、保守性、安全性を最優先とします。
2. **最適化領域 (Hot Path):** `ParallelAudioComparisonEngine` や `FastWaveCompare` などの音声比較ループ、`WaveValidation` 等の演算処理では、C#の安全機構を必要に応じて意図的にバイパスし、CPU（SIMD）とメモリの限界を引き出します。

この二面性から生じる実装の複雑さやメモリ破壊のリスクは、**AIによる積極的なコード生成と厳密なレビューを前提とする**ことで相殺します。また、最適化においては「統合テスト（V1.0.0.0との決定論的出力の一致検証）」の合格を絶対条件とし、リグレッションを徹底的に防止します。

## 1. 基盤コーディング規約 (通常領域向け)

このセクションでは、アプリケーション全体の品質を底上げするための標準的なアプローチを定義します。

### 1.1 最新言語機能のデフォルト化と「IDE警告ゼロ」の徹底

- **[What/How]**
  IDE（Visual Studio / Rider等）の静的解析がサジェストする最新のC#構文を、初期実装の段階から標準として使用します。本プロジェクトは **C# 14 / .NET 10** をターゲットとしており、具体的には以下の構文を強制し、古い記法はレビューで差し戻します。
    - **新しい排他制御 `Lock` オブジェクト (C# 13):** モニターロックに代わり、排他制御専用の `System.Threading.Lock` を使用します。
    - **`ref struct` のジェネリクスサポート (`allows ref struct`) (C# 13):** パフォーマンス向上のための `ref struct` のジェネリクス適用。
    - **拡張された `params` コレクション (C# 13):** 配列アロケーションを抑えるため、スパンや読み取り専用スパンでの `params` 適用。
    - **プライマリコンストラクター (C# 12):** `public class AudioProcessor(ILogger logger) { ... }`
    - **コレクション式 (C# 12):** `float[] buffer = [1.0f, 2.0f];`
    - **ターゲット型の `new()` (C# 9):** `WaveformConfig config = new();`
    - **パターンマッチングと `switch` 式 (C# 8+)**
    - **ファイルスコープ名前空間 (C# 10)**
    - **`required` と `init` (C# 9, 11)**
- **[Why: 設計思想と判断基準]**
  最大の理由は「ボイラープレート（無駄な定型文）の排除によるS/N比の向上」です。「最初からモダン構文で書く」ことを規約化することで、IDEを常にクリーンな状態に保ち、真に重要なパフォーマンス上の警告を見逃しません。特に C# 15 の `field` キーワードは、プロパティロジック追加時の不要なフィールド記述を消滅させ、コードの認知負荷を激減させます。また、トークン数が削減されるため、AIにコードを読み書きさせる際の精度向上とコンテキスト節約にも直結します。

### 1.2 `var` と明示的な型の使い分け

- **[What/How]**
  右辺の式から型が明確に推論できる場合やLINQの匿名型には `var` を使用します。組み込みの数値型（`int` など）や、メソッドの戻り値から型が不明瞭な場合は明示的に型を記述します。
- **[Why: 設計思想と判断基準]**
  コードを読む側（人間・AI問わず）の認知負荷を下げるためです。過度な `var` の使用は、文脈を失わせ、後からAIにコードを読み込ませて改修を依頼する際のハルシネーションの要因になり得ます。

### 1.3 実行時リフレクションの禁止とソースジェネレータ・partial プロパティの強制

- **[What/How]**
  `System.Reflection` を用いた実行時の型情報の取得やメソッド呼び出し、および従来の動的な `INotifyPropertyChanged` の実装を原則禁止します。WPFのデータバインディングや通知処理には、`CommunityToolkit.Mvvm` が提供する `ObservableObject` と `[ObservableProperty]` + `partial` プロパティ（ソースジェネレータ）を組み合わせて、コンパイル時に静的なコードを生成させます。

    ```csharp
    // Good: CommunityToolkit.Mvvm と partial プロパティによるMVVM実装
    public partial class OptimizationViewModel : ObservableObject
    {
        [ObservableProperty]
        public partial string StatusMessage { get; set; }
    }
    ```

- **[Why: 設計思想と判断基準]**
  リフレクションはCPUサイクルを大量に消費し、JITコンパイラの最適化（インライン化など）を阻害する最大の要因です。WPFのMVVMアーキテクチャやJSONシリアライズなどを静的コード生成（Source Generators）に置き換えることで、起動速度と実行時スループットを劇的に向上させます。

### 1.4 文字列操作とメモリ割り当ての抑制

- **[What/How]**
  短い文字列の組み立てには文字列補間 (`$"{}"`) を使用し、ループ内での文字列操作には必ず `StringBuilder` を使用します。
- **[Why: 設計思想と判断基準]**
  不用意な文字列連結は一時オブジェクトを大量に生成し、GCスパイク（WPFにおけるUIのカクつき）を引き起こします。

### 1.5 例外処理とエラーハンドリングの適正化

- **[What/How]**
  制御フローとして例外を使用することを禁止し、`TryParse` パターンや結果オブジェクト (`Result<T>`) を返す設計を採用します。
- **[Why: 設計思想と判断基準]**
  例外のスローはスタックトレース生成等に多大なコストがかかります。また、汎用的な `catch (Exception e)` はクリティカルなバグを隠蔽する危険性があるためです。

## 2. 波形処理の極限最適化とUIスレッドの完全分離 (Hot Path向け)

このセクションでは、標準的な安全性を犠牲にしてでもパフォーマンスを取りに行く領域のルールを定義します。**これらの実装はAIに生成・最適化させることを標準ワークフローとします。**

### 2.1 SIMD (単一命令複数データ) とハードウェア組み込み関数の強制

- **[What/How]**
  波形データの類似度比較や特徴量抽出において、スカラ処理を原則禁止し、`System.Numerics.Vector<float>` または `System.Runtime.Intrinsics`（AVX2等）を用いたベクトル化コードの実装を強制します。
  - プロジェクトの実装例: `WaveValidation` における `CalculatePearsonCorrelationSIMD` や `CalculatePearsonFromNormalizedSIMD` など。
- **[Why: 設計思想と判断基準]**
  SIMD命令を叩くことで、1クロックサイクルで複数のデータポイント（浮動小数点数）を同時処理し、波形比較の計算時間を数分の一に短縮できます。

### 2.2 バウンズチェックの意図的な排除 (Unsafe & MemoryMarshal)

- **[What/How]**
  極限のパフォーマンスが要求されるループ（Z-score正規化波形比較の高速ループや、`SilenceTrimmer` での無音領域抽出など）に限り、`unsafe` ブロックとポインタ、または `MemoryMarshal.GetReference` を用いた配列境界チェックのバイパスを推奨します。
- **[Why: 設計思想と判断基準]**
  緻密なイテレーションにおいて、境界チェックは分岐予測ミスやCPUサイクルの浪費に繋がります。AIのレビューと厳格なテストコードを前提にメモリ破壊リスクを管理し、C/C++同等のパフォーマンスを実現します。

### 2.3 ゼロアロケーションの徹底 (`ref struct` と `allows ref struct`)

- **[What/How]**
  ホットパス内で一時的に生成されるデータ構造には、`class` ではなく `struct`、さらに可能であれば `ref struct` を使用し、マネージドヒープへのメモリ割り当てを完全に禁止します。C# 13以降で利用可能となった `allows ref struct` 制約を活用し、ジェネリックな構造でも `ref struct` を扱えるようにします。
- **[Why: 設計思想と判断基準]**
  「GCスパイクを回避する最善の方法は、そもそもGCの対象を作らないこと」です。スタック割り当てにより、メソッド終了と同時に瞬時に破棄され、GC負荷をゼロにします。

### 2.4 メモリプーリング (`ArrayPool<T>`) の強制利用

- **[What/How]**
  スタックに載せきれないサイズの配列が必要な場合は `new float[size]` を絶対に使用せず、必ず `ArrayPool<T>.Shared.Rent` を使用します。
- **[Why: 設計思想と判断基準]**
  中〜大規模な配列の新規確保は、GCのLOH（Large Object Heap）を圧迫し、致命的なパフォーマンス低下を招くためです。

### 2.5 ValueTask のデフォルト化

- **[What/How]**
  高頻度で呼び出される非同期メソッド（波形ファイルのストリーム読み込みや、並列プリロード処理など）では `Task<T>` の使用を禁止し、`ValueTask<T>` をデフォルトとします。

    ```csharp
    // Good: ValueTaskによる同期完了時のゼロ・アロケーション化
    public async ValueTask<int> ReadWaveformChunkAsync(byte[] buffer, CancellationToken ct)
    {
        if (_stream.Position >= _stream.Length) return 0; // アロケーションなしで即時リターン
        return await _stream.ReadAsync(buffer, ct).ConfigureAwait(false);
    }
    ```

- **[Why: 設計思想と判断基準]**
  `Task<T>` は参照型であり、呼び出しのたびにヒープ割り当てが発生します。「実際には同期的に処理が完了する（キャッシュヒット等）」ケースが多発するホットパスにおいて、この割り当てはGCを頻発させます。構造体である `ValueTask<T>` を用いることで、同期完了時のアロケーションをゼロに抑え込めます。

### 2.6 WPF UIスレッドの完全保護と `Channel<T>` による非同期ストリーミング

- **[What/How]**
  音声比較や最適化シミュレーションなどの重いCPU/IOバウンドタスクは `Task.Run` でバックグラウンドに逃がし、UIへの進捗やログの受け渡しには `Channel<T>` を使用した非同期バッチ処理を採用します。ライブラリ側の非同期メソッドには `ConfigureAwait(false)` を徹底します。
  - プロジェクトの実装例: `PerformanceDebugLogger` における `Channel<string>` を用いた非同期ログキュー処理。
- **[Why: 設計思想と判断基準]**
  重い処理がUIスレッドをブロックすることによるUIフリーズを防ぐためです。`Channel<T>` のロックフリーに近い性質を利用し、UIやログファイルへ安全かつ低負荷でデータを供給します。

### 2.7 新しい `System.Threading.Lock` 型による高速な排他制御

- **[What/How]**
  スレッド間の同期処理において、従来の `lock (object)` 構文（モニターロック）を非推奨とし、.NET 9 / C# 13 で導入された専用の `System.Threading.Lock` クラスを強制します。

    ```csharp
    // Good: 新しい Lock オブジェクトを使用した高速な排他制御
    private readonly Lock _waveformSyncObj = new();
    public void UpdateWaveformMetadata(WaveformMetadata data)
    {
        lock (_waveformSyncObj)
        {
            _currentMetadata = data;
        }
    }
    ```

- **[Why: 設計思想と判断基準]**
  従来の `object` を用いたロックは汎用的すぎるためパフォーマンスの観点で最適ではありません。新しい `Lock` 型は排他制御に特化した設計となっており、波形データの統合時や並列計算時の複数スレッドからの書き込み待機時間を最小化できます。

### 2.8 メモリ診断機能の組み込みとオンメモリキャッシュ制限

- **[What/How]**
  大量の音源をオンメモリで処理する際、メモリ使用量の暴走を防ぐために、キャッシュ表現（`CachedSoundData` など）では必ず推定メモリ使用量（`EstimatedMemoryMB`）を算出可能にし、大容量データ処理時には `PerformanceDebugLogger.CheckAndHaltIfDiagnosisTriggered` を用いたメモリ制限の動的監視・診断処理を挟みます。
- **[Why: 設計思想と判断基準]**
  音源ファイルのロード時や類似度比較時にGCが追いつかず、Out of Memoryでプロセスが強制終了するのを防ぐためです。診断しきい値（例：起動後5秒以上経過など）に達した際にメモリ使用状況のログを自動的に吐かせ、ボトルネックの検出を容易にします。

## 3. 命名規則、スタイル、およびドキュメンテーション

チーム開発およびAIとの協業において、コンテキストの解釈をブレさせないための厳格な語彙とスタイルを定義します。

### 3.1 フィールドの命名規則 (dotnet/runtime conventions)

- **[What/How]**
  .NETランタイムチームの公式標準（dotnet/runtime conventions）を全面的に採用します。

    | フィールドの種類                | 記法（Casing） | 接頭辞               | 具体例                              |
    | ------------------------------- | -------------- | -------------------- | ----------------------------------- |
    | プライベート・インスタンス      | camelCase      | `_` (アンダースコア) | `_totalCount`, `_userName`          |
    | プライベート・静的 (static)     | camelCase      | `s_`                 | `s_cacheDirectory`, `s_initialized` |
    | スレッド静的 (ThreadStatic)     | camelCase      | `t_`                 | `t_perThreadBuffer`                 |
    | 定数 (const) / 読み取り専用静的 | PascalCase     | なし                 | `MaxRetries`, `DefaultTimeout`      |
    | パブリック / プロテクテッド     | PascalCase     | なし                 | `IsActive`, `StandardOutput`        |

- **[Why: 設計思想と判断基準]**
  C#における命名の根底には「外部に見せる顔（パブリック）は美しく、内部の作業スペース（プライベート）は効率と安全性を重視する」という明確な境界線があります。
    1. **ローカル変数との明確な分離:** `_` を付与することで、コンストラクタやメソッド内での引数との名前衝突を防ぎ、冗長な `this.` の記述を排除します。これによりコードのS/N比が向上します。
    2. **静的状態への警戒:** `s_` や `t_` を設けることで、バグやパフォーマンス劣化の温床になりやすい「共有状態（静的フィールド）」へのアクセスを、コードレビューやAI解析の際に視覚的に際立たせます。
    3. **IDE・静的解析との親和性:** 現代のコード解析（EditorConfig等）のデフォルト設定と完全に合致しており、「IDE警告ゼロ」という基盤方針（1.1）を自然に達成できます。

### 3.2 コードフォーマットとドキュメンテーション

- **[What/How]**
    - インデントは4つのスペースを使用します。
    - 中かっこは Allman スタイルを採用します。
    - すべてのパブリックメンバーにはXMLコメントを付与します。
- **[Why: 設計思想と判断基準]**
  フォーマットの一貫性は、AIがコードをパースする際のエラー（ハルシネーション）を減らします。XMLコメントは、単なる説明ではなく、後日AIにリファクタリングや最適化を依頼する際の「Ground Truth（正解データ・仕様の絶対的基準）」として機能します。

### 3.3 ADRAnchor 属性による設計決定の追跡 (ADR Traceability)

- **[What/How]**
  本プロジェクトの主要なクラス、モデル、または高度な最適化が適用されている箇所には、必ず `[ADRAnchor("ID", nameof(ClassName))]` 属性を付与します。
  
  ```csharp
  // Good: ADRAnchorによる設計決定の紐付け
  [ADRAnchor("OPT-11", nameof(ParallelAudioComparisonEngine))]
  public partial class ParallelAudioComparisonEngine
  {
      // ...
  }
  ```

- **[Why: 設計思想と判断基準]**
  「なぜこの設計になったのか」「どのようなトレードオフが検討されたのか」をドキュメント（ADR）とソースコード間で双方向に追跡可能にするためです。これにより、コード変更時に関連するADRの制約や意図を即座に把握し、設計の崩壊や意図しないデグレードを防止します。

## 4. 検証優先の原則 (Safety & Deterministic Alignment)

最適化領域（Hot Path）であっても、コードの「正当性」と「決定論的出力」は常に最優先されます。

### 4.1 統合テストによるリグレッション防止の最優先

- **[What/How]**
  最適化の変更を導入する際は、必ず 570 件以上の統合テスト（過去リリースバージョンとの決定論的一致検証）を実行し、1件の失敗も許容しません。どれほど計算速度やメモリ効率が向上する最適化であっても、精度低下や出力の不一致が発生する場合は、その最適化アプローチの採用を見送ります。
  - 実例：メモリキャッシュ効率の最大化を図る SoA (Structure of Arrays) へのメモリレイアウト変更は、浮動小数点の丸め誤差やメモリアクセス境界の変化により統合テストが一部失敗したため、採用を見送り (Rejected) としました（ADR OPT-11）。
- **[Why: 設計思想と判断基準]**
  本ツールは音ゲー（BMS）の譜面定義と音源を最適化・統合するツールであり、出力される音声や定義の不一致はプレイ体験の致命的な劣化（音が鳴らない、ズレる等）に直結します。数学的に完璧な再現性と品質を保証することが、最速の計算速度を得ることよりも優先されます。

### 4.2 ROI（投資対効果）と複雑さのトレードオフ評価

- **[What/How]**
  ホットパスの局所的な最適化を行う前に、システム全体におけるその処理の「実行時間割合」を計測します。前段の枝刈りやアルゴリズム的改善によってすでに実行頻度が極めて少なくなっている箇所については、どれほど効率的な最適化であっても、コードの複雑化やバグ混入リスクを避けるため採用を見送ります。
  - 実例：FFTアライメントの階層化（Coarse-to-Fine Alignment）は、前段のカスケード分類（Anti-Set や SimHash256 等）でほとんどのペアが枝刈りされ、実行頻度が激減したため、開発コストとリスクを考慮し不採用としました（ADR OPT-11）。
- **[Why: 設計思想と判断基準]**
  無駄な最適化は、コードの可読性を著しく下げ、将来のメンテナンスコスト（技術負債）を増大させます。最もインパクトのあるボトルネックのみをターゲットとし、シンプルさを保ちます。
