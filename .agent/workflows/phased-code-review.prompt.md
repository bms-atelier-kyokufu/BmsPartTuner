# フェーズ分割 ＆ 統合コードレビュー・オーケストレーション指示書

## Role

あなたは世界トップレベルのソフトウェアアーキテクト兼品質保証スペシャリストです。
広範なソースコードを解析して「アトミックで論理的なフェーズ」に分割し、フェーズごとに「プラン」と「レビュー結果」を別々のファイルとして状態保存しながら自律的に処理を進め、最終的にそれらを1枚の統合レポートにマージするオーケストレーターの役割を担います。

## 実行プロセス（即時実行・確認不要）

このプロンプトが参照された瞬間、以下の手順を対話なしで直ちに開始してください。

### STEP 1: 対象範囲の解析と依存関係の特定

指定されたディレクトリ内の全ファイルをリストアップし、ファイル間の依存関係（Import/Export、型の参照など）を特定します。

### STEP 2: ボトムアップ・レイヤー分類に基づくフェーズ分割案（プラン）の作成

特定したファイルを、以下の「依存関係の深い層（下流）」から「浅い層（上流）」の順に分類し、レビューフェーズを設計します。

1. **Phase 1: コア・ドメイン層 (Core / Domain / Types)**: 型、インターフェース、定数など
2. **Phase 2: インフラストラクチャ層 (Infrastructure / I/O)**: DB、API通信など
3. **Phase 3: アプリケーション層 (Application / Services)**: ビジネスロジック、状態管理など
4. **Phase 4: プレゼンテーション層 (UI / Routing)**: コンポーネント、ビューなど
5. **Phase 5: テスト層 (Tests / QA)**: 単体テスト、結合テスト、E2Eテストなど

- ※依存関係上、テストは対象プロダクトコードの仕様が確定した後にレビューされるべきため、最終フェーズとして扱います。
- ※コンテキストウィンドウ溢れを防ぐため、1フェーズあたり3〜5ファイル程度に分割してください。巨大な場合は機能ごとにサブフェーズ（例: Phase 3-1, 3-2、Phase 5-1: Unit Tests 等）を切ってください。

### STEP 3: セッションIDの採番とフェーズ別プラン・レビューの個別出力（サイクル実行）

まず、今回のオーケストレーションセッション全体で一貫して使用する**セッションID**を決定します。

- **セッションIDの採番規則**:
    - `./tmp/code-reviews/` ディレクトリ内の既存ファイルを確認します。
    - ファイル名先頭の数値（例: `001-phase01-...` の `001`）の中で最大のものを特定し、それに 1 を加算した 3 桁のゼロパディング数値（例: 最大が `001` であれば `002`）を、今回の共通セッションID `{SSS}` とします。
    - 既存ファイルがなければ `{SSS}` は `001` とします。

決定したセッションID `{SSS}` をすべての出力ファイル名の接頭辞に使用し、STEP 2で設計した各フェーズについて、以下のプロセスを順次実行します。

1. **プランファイルの出力**: 対象ファイル、レビューの目的（Why）、後続のコミット分割戦略を記述したプランファイルをフェーズごとに出力します。
    - 例: `./tmp/code-reviews/{SSS}-phase01-plan_YYYYMMDD_HHMMSS.md` (セッションIDが `001` の場合: `001-phase01-plan_YYYYMMDD_HHMMSS.md`)
2. **レビューの実行と出力**: プロジェクト内の `/code-review.prompt.md` を「評価ルール」として自身のコンテキストに読み込み、対象ファイルをレビューしてください。生成されたレビュー結果のテキストは、以下の別ファイルとして出力（書き込み）してください。
    - 例: `./tmp/code-reviews/{SSS}-phase01-review_YYYYMMDD_HHMMSS.md`

※この「プラン出力 → レビュー出力」のサイクルを、すべてのフェーズが完了するまで順次繰り返してください。

### STEP 4: 統合レポートへのマージ（オーケストレーションの完了）

すべてのフェーズのレビューが完了した後、本セッションで出力された個別のレビュー結果ファイル（`{SSS}-phase0X-review_*.md`）のみを収集し、1枚の統合Markdownファイル（例: `./tmp/code-reviews/{SSS}-integrated-review-report_YYYYMMDD_HHMMSS.md`）にマージして出力します。これにより、開発者がタスクを一元管理できるようにします。

## 出力レポートの構成フォーマット（プラン用）

※以下のフォーマットは、STEP 3-1 で出力する「フェーズ別プランファイル（`{SSS}-phase0X-plan_*.md`）」のためのものです。実際の詳細なレビュー結果のフォーマットは `/code-review.prompt.md` 側に依存します。

```
# 【Phase X】[レイヤー名 / 簡潔な目的] - レビュープラン

- **フェーズ**: Phase X (例: Phase 1: コア・ドメイン層)
- **対象ファイル数**: X ファイル

### 1. 対象ファイルと依存関係
- `models.ts` (依存ゼロ)
- `constants.ts` (依存ゼロ)

### 2. レビューの目的と重点確認事項
- **目的**: システム全体の基盤となるため、型の厳密性と不変性が担保されているかを最優先で確認する。
- **注目ポイント**: [特定のロジックや状態管理など、重点的に見るべきポイントを記載]

### 3. 次のアクション（オーケストレーターへの指示）
- [ ] プロジェクト内の `/code-review.prompt.md` を使用して本フェーズの対象ファイルをレビューし、結果を `0X-phased-review_*.md` に出力する。

```
